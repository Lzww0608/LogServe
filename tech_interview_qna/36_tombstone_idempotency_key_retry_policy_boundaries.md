# 36. tombstone、idempotency key 与 retry policy 追问链

这一组问题看起来分散，其实都在考同一件事：系统在失败、删除、超时和重试之间，怎样避免把已经删除的数据读回来，怎样避免把一个业务动作执行两次，怎样避免用“自动恢复”制造更大的事故。tombstone 是存储层的删除语义，idempotency key 是接口层的去重语义，retry policy 是调用层的失败控制语义。三者都不能只背一句话，必须说清作用范围、保留条件、过期条件和事故边界。

## Q001. 面试官如果只问一个问题检验你是否理解 tombstone，可能会问什么？

我觉得最能检验理解的问题是：在一个 LSM 或 append-only KV 里，用户删除了 key，为什么系统通常先写一个 tombstone，而不是直接把旧值从磁盘文件里删掉？这个 tombstone 什么时候才能安全删除？

这个问题能把 tombstone 的核心都带出来。append-only 或 LSM 型存储里，旧值可能已经散落在多个不可变文件、多个 level、多个 segment 里。删除操作如果要立即把所有旧值都物理移除，就会变成随机改写大量文件，直接破坏这类存储结构依赖的顺序写和不可变文件模型。因此系统先写入一个更“新”的删除标记，用它遮住更旧的 value。读路径看到这个 key 时，要按版本顺序判断：如果最新可见记录是 tombstone，那么逻辑结果就是不存在，即使更老的文件里还有旧值。

真正难的地方在后半句：什么时候能删 tombstone。答案不是“下一次 compaction 就删”。只有当系统能证明所有被它遮蔽的旧版本都已经不可能被任何读者看到，tombstone 才能被回收。这里的读者不只是当前普通查询，还包括 snapshot、迭代器、备份、复制、CDC、慢副本、恢复流程，甚至某些仍在读取旧版本文件的后台任务。

如果 tombstone 删除得太早，旧值可能从更老的 SSTable 或 segment 里重新冒出来，表现成“删除后复活”。如果 tombstone 一直不删，它会增加空间占用、读放大和 compaction 成本。面试里我会明确说：tombstone 不是垃圾，也不是最终数据；它是一个带安全回收条件的删除证据。

这个问题还会考出一个边界：tombstone 的范围是什么。点删除只覆盖一个 key；range tombstone 覆盖一段 key range；TTL 过期可以被实现成逻辑删除或 compaction filter；日志压缩系统里的 delete marker 还要考虑消费者是否已经读到删除事件。范围不同，回收条件和事故形态也不同。

所以我会这样回答：tombstone 的存在，是为了在不可变文件和多版本读的模型里表达删除；它的安全删除点，取决于被遮蔽旧值、快照、复制、备份和所有观察者的推进状态，而不是取决于“我已经写了一条删除记录”这个事实本身。

## Q002. tombstone 的一句话定义是否容易误导，误导点在哪里？

容易误导。最常见的定义是：tombstone 是删除标记。这个定义太短，容易让人以为它只是一个临时占位符，或者以为它写入以后旧数据就已经不存在了。

第一个误导点是把“逻辑删除”和“物理删除”混在一起。tombstone 写入以后，用户语义上可以看不到旧值，但底层旧值很可能还在磁盘文件里。读路径之所以返回不存在，是因为新版本的删除标记遮住了旧版本，不是因为旧文件马上被改写了。物理回收通常要等 compaction 或 segment 清理完成。

第二个误导点是忽略可见范围。一个 tombstone 对谁可见，取决于版本号、LSN、offset、snapshot 或事务时间点。老 snapshot 可能仍然能看到删除之前的值；新读者应该看到删除后的结果；复制链路上的下游系统需要先收到删除标记，才能正确删除自己的副本。如果只说“删除标记”，就说不清这些观察者之间为什么会看到不同结果。

第三个误导点是把 tombstone 当成“可以随时清掉的垃圾”。它确实会带来空间和读放大，但它同时承载正确性。只要更旧的 value 仍有机会被读路径、恢复流程或下游消费者看到，tombstone 就不能随便丢。很多删除复活事故，本质都是把 tombstone 当成普通垃圾清理了。

第四个误导点是只把它限定在 LSM。tombstone 在很多系统里都有类似角色：日志压缩主题里，null value 或 delete marker 表示 key 的删除；文档库和搜索索引可能用 delete bitset 或删除段记录；CDC 里可能要传播删除事件；对象存储或元数据系统里也可能通过删除记录保护幂等和恢复。实现形式不同，但问题都一样：删除语义必须先被可靠传播，再谈物理回收。

我更愿意把它定义为：tombstone 是一种参与版本可见性判断的删除证据，它让系统在无法立即改写所有旧数据时，仍然能提供正确的删除语义。它什么时候被写、对谁可见、什么时候能被回收，才是定义里最重要的部分。

## Q003. tombstone 最常见的生产事故触发条件是什么？

最常见的事故可以分成两头：一头是删得太早，导致旧值复活；另一头是删得太晚，导致空间、读放大和 compaction 压力失控。

删得太早通常发生在 compaction 或清理逻辑把安全条件想简单了。比如系统看到某个 level 里已经没有旧值，就把 tombstone 丢掉，但更老的 level、备份视图、慢副本或某个 snapshot 还可能看到被遮蔽的 value。下一次读、恢复或重放时，旧值就可能重新成为“最新可见值”。这种事故表面上像读路径偶发错误，根因往往在回收条件没有覆盖所有观察者。

删得太晚也很常见。长时间 snapshot、慢消费的 CDC、落后的副本、长事务、持续 range scan，都可能把旧版本钉住。大量 tombstone 留在系统里以后，点查 miss 要反复撞删除标记，范围查询要跳过大量墓碑，compaction 要不断携带这些删除记录，磁盘也迟迟不能回收。用户看到的是查询变慢、磁盘水位上涨、后台任务跑不完。

删除风暴是第三类高频触发条件。TTL 同时到期、批量删除租户数据、清理历史消息、误配置的保留策略，都可能在短时间内制造海量 tombstone。它们一开始可能让前台删除很快，但后续 compaction、索引更新、缓存污染和空间回收会集中爆发。系统如果没有限速、分批、后台预算和水位保护，事故会从删除接口扩散到整个存储引擎。

range tombstone 和 TTL 还容易带来边界错误。range 删除如果和 comparator、前缀编码、分区边界、半开区间定义不一致，就可能多删或漏删。TTL 如果依赖本地时间，时钟漂移或跨节点时间差会让数据过早过期或迟迟不过期。compaction filter 如果在版本升级时改变解释规则，也可能让旧数据的删除判断变得不稳定。

还有一类是复制和下游系统没跟上。上游认为某个 tombstone 已经可以清理，但下游消费者还没看到删除事件，或者灾备恢复点还停在删除之前。这样一来，主库清理看似正确，恢复出来的副本却可能保留旧值。

所以 tombstone 的生产事故触发条件通常不是“删除语句本身失败”，而是删除语义在多版本、多观察者、多阶段回收之间没有被完整建模。

## Q004. tombstone 的指标应该怎么设计才不会只看平均值？

tombstone 的指标不能只看“当前有多少删除标记”。数量只是入口，真正要看的是年龄、范围、分布、被谁钉住、在读路径里造成了多少成本，以及最终能不能被安全回收。

第一组指标是存量和分布。要按表、租户、partition、key range、level 或 segment 统计 tombstone count、tombstone bytes、range tombstone count、TTL 生成的删除数量、点删除和范围删除比例。全局平均值没有太大价值，一个租户的删除风暴完全可能被全库平均掩盖。

第二组是年龄和安全水位。要看 oldest tombstone age、oldest snapshot age、oldest pinned sequence、最慢副本位置、最慢 CDC offset、备份保留点、恢复保留点。一个系统里 tombstone 是否能清理，往往不是由新请求决定，而是由最慢的观察者决定。这里必须看最大值和长尾，不能只看平均年龄。

第三组是读路径成本。点查和范围查要分别统计每次查询遇到的 tombstone 数、被 tombstone 遮蔽的旧版本数、因删除标记产生的额外文件探测、filter 命中后发现删除的比例、range scan 跳过的删除记录数。读延迟也要拆 p95、p99 和 max，因为 tombstone 对 miss-heavy 查询和宽范围扫描的影响远大于对热 key 命中的影响。

第四组是回收效果。compaction 中要统计 tombstone carried、tombstone dropped、被保留的原因、删除后实际释放的 bytes、obsolete value bytes、space amplification、pending compaction bytes。很多系统以为自己在清理，实际上 compaction 只是把 tombstone 从一层搬到另一层，没有真正释放空间。

第五组是正确性保护指标。可以有 delete resurrection check、删除后读旧值的异常计数、下游删除事件滞后、同一 key 删除后又出现旧 sequence 的告警、range delete 边界校验失败。生产系统里这类指标很少，但面试里说出来会体现你知道 tombstone 不是单纯性能问题。

我会把 tombstone 面板设计成三条主线：删除标记积压了多少、为什么还不能删、它对读和 compaction 造成了多少尾部成本。只有这三条都看，才不会被平均延迟和平均空间使用率骗过去。

## Q005. tombstone 的正确性边界和性能边界分别是什么？

tombstone 的正确性边界是：在所有应该看不到旧值的读者面前，旧值必须被删除标记遮住；在所有仍然有权看到旧视图的读者面前，系统又不能破坏它们的历史可见性。这个边界听起来绕，但它正是多版本存储的本质。

对新读者来说，tombstone 是最新可见版本时，结果就应该是不存在。对旧 snapshot 来说，如果它建立在删除之前，可能仍然应该看到旧值。对复制和 CDC 来说，下游必须先接收并处理删除记录，才能在自己的存储里删除对应 key。对恢复来说，WAL、manifest、SSTable 或 segment 的组合必须能重建出同样的删除语义。

因此 tombstone 的安全回收点必须满足几个条件：被它遮蔽的旧版本已经不会被当前读路径选中；所有需要旧视图的 snapshot 已结束；所有依赖删除事件的下游观察者已经越过相应位置；备份和恢复策略不再需要这个删除证据；range tombstone 的边界和 comparator 解释没有歧义。任何一条没满足，回收都可能变成数据复活或下游不一致。

性能边界则在成本上。tombstone 能让删除前台很快，但它把成本转移到了读、compaction 和空间回收。删除比例低时，这个成本可能很小；删除比例高、TTL 集中过期、长 snapshot 存在时，tombstone 会显著增加读放大和空间放大。范围删除还能在短期内很便宜，但后续查询如果频繁穿过被删除范围，跳过成本会很明显。

太激进和太保守都会出问题。太激进会复活旧数据；太保守会让磁盘和尾延迟恶化。一个成熟系统通常要把 tombstone 回收和 snapshot 生命周期、复制水位、compaction 预算、磁盘水位、租户限流放在一起设计。

如果放到 LogServe 这类日志和恢复语义里，我会把 tombstone 类比成“删除或失效事实”的持久证据。它不能只服务当前内存状态，还要服务崩溃恢复、重放、下游消费和审计边界。正确性边界要求证据不能早丢，性能边界要求证据不能无限堆积。

## Q006. 面试官如果只问一个问题检验你是否理解 idempotency key，可能会问什么？

我会期待面试官问这个问题：客户端发起创建订单请求，服务器可能已经创建成功，但响应在网络上超时了。客户端用同一个 idempotency key 重试，不过第二次请求的 payload、租户、region 或业务参数发生了变化，服务端应该怎么处理？

这个问题比“什么是幂等键”更有区分度，因为它会逼你说清 idempotency key 的作用范围。幂等键不是一个全局魔法字符串，它必须绑定到某个业务动作、某个接口、某个租户或账号、某组请求参数，以及一段有限的保留时间。服务端看到同一个 key 时，第一步不是盲目执行，也不是简单返回成功，而是先查这个 key 对应的第一次请求是什么状态。

如果第一次请求已经完成，并且第二次请求的作用域和请求指纹一致，服务端应该返回第一次请求的结果。这里的结果通常包括状态码、响应体、业务资源 ID，甚至可能包括第一次失败的结果。这样客户端即使没收到第一次响应，也能通过重试收敛到同一个业务结果。

如果同一个 key 带着不同 payload 或不同业务作用域再次出现，正确做法通常是拒绝，并报告 idempotency key 与请求参数不匹配。否则一个 key 可能先代表“创建 100 元订单”，又代表“创建 200 元订单”，服务端无论返回哪一个结果都会制造语义混乱。这里不能靠客户端自觉，服务端必须保存足够的请求指纹来校验。

如果第一次请求还在处理中，服务端要有 in-progress 状态。它可以让第二个请求等待、返回冲突、返回正在处理，或者根据系统设计做短暂轮询，但不能让两个线程同时通过检查然后各自创建一笔订单。幂等记录和业务写入之间要有事务、唯一约束或等价的原子保护。

TTL 也是这个问题里的陷阱。idempotency key 不可能无限保存，但过期以后，服务端就不能再承诺旧 key 的去重效果。客户端如果在 TTL 之后用同一个 key 重试，系统可能把它当成新请求；这时文档、SDK 和业务流程都要明确这个边界。

所以我会回答：idempotency key 的核心不是“重复请求返回同样结果”这句话，而是服务端用一个有作用域、有请求指纹、有状态机、有保留期的记录，把一次不确定的业务提交收敛成一个可重复查询的结果。

## Q007. idempotency key 的一句话定义是否容易误导，误导点在哪里？

容易误导。常见定义是：idempotency key 用来防止重复请求。这个说法会让人误以为只要请求头里带一个随机 key，重复执行问题就自动消失了。

第一个误导点是忽略服务端持久化。幂等键只有被服务端可靠记录下来才有意义。记录至少要包含 key、作用域、请求指纹、处理状态、最终响应或业务资源引用、创建时间和过期时间。如果服务端只在内存里记一下，进程重启后就失效；如果只记 key 不记请求指纹，就无法判断同一个 key 是否被错误复用。

第二个误导点是把它和幂等方法混为一谈。某些操作天然幂等，比如把资源状态设置为某个固定值；但创建订单、扣款、发送消息这类操作通常不是天然幂等。idempotency key 是给这些非天然幂等的提交动作加一个去重协议，而不是改变业务动作本身的副作用性质。

第三个误导点是忽略并发窗口。两个完全相同 key 的请求可能同时到达。如果实现是“先查没有记录，再执行业务，再写幂等记录”，并发下两个请求都可能通过检查。正确实现通常要先占位、用唯一约束抢占 key，或者在同一个事务里写入幂等记录和业务结果。否则幂等键只是纸面设计。

第四个误导点是忽略失败结果。第一次请求如果已经进入业务逻辑，但最后返回 500、超时、进程崩溃或部分成功，重试时应该怎么响应？成熟实现要区分“请求根本没开始”“正在处理”“业务已提交但响应丢失”“业务失败且可以确定没有副作用”“结果未知”。不同状态的重试策略不同，不能统一说“返回同样结果”。

第五个误导点是忽略作用域。一个 key 在用户 A 的创建订单接口里和用户 B 的退款接口里不应该互相影响。key 的唯一性通常要和租户、账号、接口、region、业务资源类型一起定义。作用域太小会漏重，作用域太大又容易误拒绝。

我更愿意把 idempotency key 定义成：客户端为一次业务意图生成的稳定标识，服务端用它在约定作用域和保留期内识别重复提交，并通过请求指纹和持久状态保证重复提交不会产生新的业务副作用。

## Q008. idempotency key 最常见的生产事故触发条件是什么？

最常见的事故是客户端每次重试都生成新 key。这样从客户端视角看是在“重试同一个操作”，但服务端看到的是多个全新的业务提交。创建订单、创建支付、发券、发消息这类接口，一旦这样实现，就会产生重复资源或重复副作用。

第二类事故是 key 被复用到不同业务意图。比如移动端把 idempotency key 缓存在表单级别，用户改了金额或收货地址还继续用同一个 key；或者某个批处理任务把一个固定 key 用在一批不同记录上。服务端如果不校验请求指纹，就可能把第二个业务意图错误地折叠到第一个结果上；如果校验了，应该返回参数不匹配，而不是继续执行。

第三类事故是幂等记录和业务状态不一致。比如业务表写成功了，幂等表没写成功；幂等表写了处理中，业务事务回滚了；业务结果已经提交，响应还没保存，重试时服务端不知道该返回什么。这类问题经常出现在跨库、跨消息队列、跨外部支付网关的流程里。幂等键要么和业务写入在同一个事务边界里，要么通过 outbox、状态机、唯一业务约束等方式补足一致性。

第四类是并发首请求竞争。两个相同 key 的请求同时到达，如果没有唯一约束或原子占位，它们可能各自完成副作用。这个问题在网关重试、客户端双击、移动网络抖动、负载均衡重发时很常见。只在应用层加一段“查一下有没有 key”的代码，挡不住并发。

第五类是 TTL 设计不合理。TTL 太短，客户端慢重试或任务恢复时去重记录已经被清理，重复提交会变成新请求；TTL 太长，存储成本和隐私风险上升，热点 key 也可能拖慢查询。不同业务的重试窗口不一样，支付、订单、消息、批处理不能用一个拍脑袋的 TTL。

第六类是作用域缺失。多租户系统如果只用 key 本身做唯一索引，不带 tenant、endpoint、region 或业务类型，可能让不同用户互相冲突；反过来，如果 region 之间没有清楚的幂等边界，跨区重试可能在两个区域各创建一次资源。

还有一类容易被忽略：把 idempotency key 放进日志、URL 或可见错误信息里，导致隐私和安全问题。key 本身不应该承载敏感业务信息，最好是高熵随机值，再由服务端绑定请求指纹。

所以 idempotency key 的生产事故通常不是“没有 key”，而是 key 的生成时机、作用域、持久化、并发控制和业务事务边界没有一起设计。

## Q009. idempotency key 的指标应该怎么设计才不会只看平均值？

idempotency key 的指标要围绕“重复请求是否被正确折叠”和“去重系统本身是否成为瓶颈”来设计，不能只看接口平均延迟。

第一组是去重效果指标。要看 idempotency hit rate、首次请求数量、重复请求数量、同 key 同指纹重放数量、同 key 不同指纹拒绝数量、in-progress 冲突数量、TTL 过期后再次出现的数量。这些指标要按 endpoint、tenant、client version、region、业务类型拆分。全局命中率高不一定是好事，可能是客户端网络差，也可能是上游超时太短造成大量重复提交。

第二组是状态机指标。幂等记录通常会经历 created、in-progress、succeeded、failed、unknown、expired 等状态。要看各状态的存量、停留时间、超时迁移数量、unknown 状态比例。尤其要看 in-progress 的 p95、p99 年龄和最长年龄；平均处理时间正常，不代表没有一批 key 卡在处理中，导致客户端一直拿不到确定结果。

第三组是请求指纹和作用域指标。参数不匹配次数、跨租户冲突次数、跨 region 冲突次数、重复 key 被错误复用次数，都应该单独告警。它们不是普通 4xx 噪声，而是客户端 SDK、调用方或业务流程可能在破坏幂等协议。

第四组是存储和性能指标。幂等表或缓存的 lookup latency、write latency、事务冲突、唯一键冲突、存储错误、容量、索引膨胀、清理耗时、TTL prune 数量都要看 p95、p99 和 max。幂等系统通常在故障和重试风暴时压力最大，平时平均延迟没有说明力。

第五组是业务副作用指标。比如重复订单被阻止数量、重复扣款被阻止数量、同一业务资源多次创建异常、幂等记录存在但业务结果缺失、业务结果存在但幂等记录缺失。仅看技术层命中率不够，最终要看它有没有真的保护业务不重复执行。

第六组是安全和治理指标。key 长度不合规、低熵 key、可疑重复模式、包含敏感字段的 key、异常高基数租户，都值得记录。幂等键通常来自外部客户端，不能假设它永远规范。

我会把面板分成四块：重复提交行为、幂等状态机、存储性能、业务重复副作用。这样看出来的不是“平均请求还挺快”，而是“某个接口的重试正在被正确折叠，还是正在制造重复业务结果”。

## Q010. idempotency key 的正确性边界和性能边界分别是什么？

idempotency key 的正确性边界是：在约定作用域和保留期内，同一个业务意图只能产生一次业务副作用，后续重复提交必须收敛到第一次的确定结果。这里有几个词不能省：约定作用域、保留期、同一个业务意图、确定结果。

“同一个业务意图”要靠请求指纹确认。不能只看 key 字符串相等，还要确认 endpoint、tenant、账号、业务类型、关键参数一致。否则 key 复用会把不同操作误合并。“确定结果”也不是永远成功，它可能是第一次成功的资源，也可能是第一次确定失败的错误。关键是重试不能再创建第二个资源或第二次扣款。

幂等记录和业务副作用之间的原子性是正确性核心。如果先执行业务再写幂等记录，崩溃会留下无法识别的成功；如果先写成功记录再执行业务，重试可能返回一个并不存在的结果。实际设计通常需要数据库唯一约束、事务、状态机、outbox、业务唯一键或外部系统的幂等能力配合，单靠一个 HTTP header 不够。

它也不是 exactly-once 的同义词。幂等键可以让客户端重复提交收敛到一次业务结果，但网络仍可能重复传输，请求仍可能被多次接收，内部步骤仍可能重试。它保证的是“可观察业务副作用不重复”，不是所有底层执行步骤只运行一次。

性能边界在于每个受保护的写接口都要多一次幂等查询和状态写入。高 QPS 下，幂等表可能成为热点；某些 key 被大量重复请求打中时，也可能形成热点行或锁竞争。保存完整响应体会增加存储成本，只保存资源引用又要求后续能稳定重建响应。缓存可以减轻压力，但缓存不能替代持久状态。

TTL 是性能和正确性的交界。保留时间越长，重复提交保护越强，存储和隐私成本越高；保留时间越短，清理越轻，但慢重试、离线恢复和延迟队列更容易越过边界。TTL 必须和客户端重试窗口、消息重放窗口、业务争议窗口一起定。

所以我会总结：idempotency key 的正确性边界是一次业务意图在一个作用域内的收敛语义；性能边界是为了这个收敛语义付出的持久查写、锁竞争、存储保留和热点 key 成本。它是提交协议的一部分，不是请求头上的装饰。

## Q011. 面试官如果只问一个问题检验你是否理解 retry policy，可能会问什么？

我觉得最有效的问题是：一次 RPC 超时了，你会不会重试？如果会，哪些错误码能重试，最多重试几次，每次间隔怎么定，总 deadline 怎么算，业务是否幂等，服务端已经执行成功但响应丢了怎么办？

这个问题能把 retry policy 从“失败了再试一下”拉回工程现实。超时并不等于服务端没有执行。请求可能已经到达服务端，业务也可能已经提交，只是响应在网络上丢了，或者客户端 deadline 先到了。如果这个 RPC 是创建订单、扣款、发消息，盲目重试可能直接制造重复副作用。

所以第一步是判断操作是否可安全重试。读请求、幂等更新、带条件写入、带 idempotency key 的创建请求，通常更适合重试；非幂等写、外部副作用不可确认的调用、已经进入提交阶段但结果未知的操作，不能只靠 retry policy 兜底。需要幂等键、资源唯一约束、条件请求、事务状态查询或补偿流程配合。

第二步是定义可重试错误。连接断开、临时不可用、资源耗尽、网关超时、服务端明确提示稍后再试，这些可能是候选；参数错误、权限错误、业务校验失败、资源不存在这类永久错误，重试通常只会放大压力。状态码也不能机械判断，同一个 500 可能代表请求未执行，也可能代表执行后响应序列化失败。

第三步是控制时间和次数。每个请求要有总 deadline，单次 attempt 也要有 timeout。不能让每次重试都重新拿到完整超时时间，否则上游早就放弃了，下游还在处理一串过期请求。max attempts、指数退避、jitter、服务端 Retry-After、retry budget 都要一起出现。

第四步是避免重试风暴。故障时所有客户端同时重试，如果没有退避和抖动，流量会一波一波打到已经不健康的服务上。更糟糕的是多层系统都各自重试，客户端重试三次，网关重试两次，SDK 再重试两次，一个逻辑请求就可能变成十几次下游调用。

所以我会回答：retry policy 的核心不是“失败就重试”，而是只在语义安全、错误可恢复、时间预算允许、系统负载能承受的前提下，把一次不确定调用变成受控的多次尝试。

## Q012. retry policy 的一句话定义是否容易误导，误导点在哪里？

容易误导。常见定义是：retry policy 是请求失败后的重试规则。这个定义的问题是，它把重试说成了一个局部动作，好像只要配置次数和间隔就够了。

第一个误导点是把失败当成确定状态。网络调用里的失败经常是不确定的：客户端没收到响应，不代表服务端没执行；代理返回超时，不代表后端没提交；连接断开，也可能发生在响应写回阶段。如果 retry policy 不理解这种不确定性，就会把“查询结果未知”误处理成“操作未发生”。

第二个误导点是忽略业务语义。重试读请求和重试扣款请求完全不是一件事。技术上同样是一次 HTTP 或 RPC 调用，业务上可能一个没有副作用，一个会创建资源。retry policy 必须知道操作是否幂等，是否有 idempotency key，是否有条件写入，是否允许重复执行。

第三个误导点是把重试次数当成可靠性来源。重试确实能掩盖瞬时网络抖动和短暂负载不均，但它不能修复容量不足、依赖长期不可用、永久性参数错误或数据约束冲突。对这些问题不断重试，只会增加排队、放大延迟、拖垮下游。

第四个误导点是忽略总时间预算。很多配置只写 max attempts 和 backoff，却没有全局 deadline。结果调用方等了很久，下游还在处理已经没有业务价值的请求。正确的 retry policy 应该先有总预算，再把预算分给每次尝试和退避间隔。

第五个误导点是忽略系统层级。客户端 SDK、网关、服务 mesh、负载均衡、gRPC 框架、业务代码都可能配置重试。如果每层都觉得自己只是“轻微重试一下”，最终的请求放大倍数会很惊人。retry policy 必须作为端到端策略治理，而不是每层各配各的。

所以我更愿意把 retry policy 定义成：在明确错误分类、业务幂等性、时间预算和负载保护的前提下，对一次失败或结果未知的调用进行受控再尝试的策略。它是可靠性工具，也是流量放大器，用错了就是事故源。

## Q013. retry policy 最常见的生产事故触发条件是什么？

最常见的是重试非幂等操作。比如创建订单、扣款、发短信、发消息、发放优惠券，一次超时以后客户端又发一次，如果没有 idempotency key 或业务唯一约束，就可能产生重复副作用。很多事故不是服务端真的处理错了，而是客户端把“不知道成功没成功”当成“肯定失败”来处理。

第二类是重试风暴。依赖服务短暂抖动，客户端、网关和上游服务同时开始重试，流量瞬间变成原来的几倍甚至十几倍。下游本来只是慢，现在被重试流量压成不可用；不可用又触发更多重试，形成正反馈。没有 jitter、没有 retry budget、没有并发限制、没有熔断时，这类事故特别容易扩散。

第三类是超时配置反向放大。客户端 timeout 设得比服务端正常处理时间还短，请求刚进入服务端还没处理完，客户端就超时重试。服务端同时处理多个相同业务意图，延迟继续升高，客户端继续重试。表面看是“服务端慢”，根因可能是 timeout 和重试策略把正常慢请求变成了并发重复请求。

第四类是重试永久错误。参数错误、权限错误、配额不足、业务状态不允许、资源不存在，这些错误重试多少次也不会成功。把它们放进 retryable 列表，会浪费资源，还会污染告警。限流错误也不能简单重试，要尊重服务端退避提示和客户端预算，否则就是对限流系统的对抗。

第五类是嵌套重试。业务代码重试三次，SDK 重试三次，服务 mesh 重试两次，下游数据库驱动再重试一次，一个逻辑请求的真实尝试次数可能远高于面板显示。事故发生时，团队常常只看到最外层请求量没有暴涨，却没看到下游 attempt 数已经被放大。

第六类是忽略幂等状态查询。有些操作在超时后应该先查询业务状态，而不是立刻重发提交请求。比如支付、订单创建、任务提交，客户端可以用业务订单号或 idempotency key 查询第一次请求的结果。没有这个步骤，retry policy 就会把结果未知的状态粗暴转成重复提交。

所以 retry policy 的事故触发条件通常不是“没有重试”，而是重试对象、错误分类、时间预算和系统负载保护没有被一起约束。

## Q014. retry policy 的指标应该怎么设计才不会只看平均值？

retry policy 的指标要以“一个逻辑请求被放大成了多少次真实尝试”为中心。只看最终成功率和平均延迟，很容易把重试带来的下游压力隐藏掉。

第一组是 attempt 指标。要看每个 logical request 的 attempt count 分布，尤其是 p95、p99、max；要按 endpoint、依赖服务、错误码、客户端版本、租户拆分。平均 attempt 接近 1 没有说明力，因为少量故障接口可能已经在尾部请求里重试很多次。

第二组是重试原因和结果。要看 retry rate by status code、timeout retry、connection error retry、throttling retry、server unavailable retry，以及 retry 后成功、retry 后仍失败、因 max attempts 放弃、因 deadline 放弃、因 retry budget 放弃的比例。这样才能判断重试是在恢复瞬时故障，还是在掩盖永久错误。

第三组是延迟成本。要把 first-attempt latency、end-to-end latency、retry added latency 分开看。用户感知的是端到端延迟，下游承受的是所有 attempts 的处理成本。重试可能提高最终成功率，同时把 p99 延迟拉得很长，这个权衡必须可见。

第四组是流量放大和负载保护。要看 retry amplification factor、in-flight attempts、下游 QPS 中重试请求占比、retry budget burn rate、被限流或熔断的重试数、因为 jitter 分散开的请求分布。故障时最重要的不是平均 QPS，而是峰值和同步程度。

第五组是语义安全指标。对非幂等或条件幂等接口，要看带 idempotency key 的比例、重复副作用被抑制数量、重复订单或重复消息异常、同一业务 key 的并发 attempts、重试前状态查询命中率。没有这些指标，retry policy 只是在技术层面看起来可控，业务层面可能已经出错。

第六组是层级治理指标。要记录是哪一层触发了重试：客户端 SDK、网关、服务 mesh、gRPC 框架、业务代码，还是数据库驱动。还要看每层的 max attempts 配置和实际生效次数。否则排障时会误以为只有一层在重试。

我会把面板设计成四个问题：重试放大了多少流量，恢复了多少成功，增加了多少尾延迟，是否仍然语义安全。四个问题都回答清楚，才算真正看懂 retry policy。

## Q015. retry policy 的正确性边界和性能边界分别是什么？

retry policy 的正确性边界是：只有当重复尝试不会改变业务语义，或者有机制把重复尝试折叠成同一个业务结果时，重试才是安全的。这个机制可以是操作天然幂等、idempotency key、条件写入、资源唯一约束、状态查询、事务状态机或补偿流程。

如果一个请求已经在服务端提交成功，只是响应丢了，下一次重试必须收敛到同一个结果，而不是创建第二个结果。如果第一次请求到底有没有提交无法判断，系统应该进入结果查询、处理中、人工补偿或恢复流程，而不是无限重发提交请求。retry policy 不能把不确定状态伪装成确定失败。

错误分类也是正确性边界。临时网络错误、服务暂时不可用、可恢复的资源不足，可能适合重试；参数错误、权限错误、业务约束失败、不可恢复的状态冲突，通常不适合。限流和过载错误要尊重服务端退避信号，否则重试会违反下游保护机制。

性能边界是：重试用额外请求换取更高的成功概率，但它同时增加延迟、下游负载、队列长度和故障扩散风险。低频瞬时错误下，少量退避重试很划算；依赖持续不可用或容量不足时，重试只会让系统更慢。retry policy 必须有 max attempts、总 deadline、指数退避、jitter、retry budget、并发限制和熔断配合。

还要注意端到端预算。一个上游请求可能串联多个下游，如果每一段都重试到自己的上限，用户请求的总延迟和总流量会失控。正确做法是从入口请求的 deadline 往下传递预算，下游在剩余预算内决定是否还有重试价值。

在 LogServe 这类有日志、恢复、后台任务的系统里，我会把 retry policy 和幂等键、租约、fencing token、任务状态机放在一起看。后台 worker 可以重试写入或投递，但必须保证同一条逻辑日志、同一个任务或同一个输出不会因为重试被重复提交。正确性边界是业务结果收敛，性能边界是重试不能压垮恢复路径本身。

所以 retry policy 的一句总结应该是：它不是可靠性的免费午餐，而是在语义安全和负载预算内，对不确定失败做有限再尝试的控制面。
